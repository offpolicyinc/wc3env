Self-Play Anatomy

How self-play works now: what runs where, how long each part takes, what limits speed and cost.
How it got here, run by run: 9-benchmarks.md.

1 · Overview

Two kinds of machine, joined by tunnels

Games run under Wine in 8 CPU sandboxes; the game hook turns each game's state into model inputs, in C.
One container with two H100s decides and learns: 16 actors on its CPU,
2 inference processes on GPU 1, the learner on GPU 0.
Today: ~7,000–7,300 steps/s from 512 games, the learner keeping up.

2 · The model

11.9M parameters, one decision per player per step

Each step, for each player, the model sees a set of tokens and makes one decision through 10 heads.

unit tokens
one per unit the player sees (own, enemy, creeps, mines): ~5 early, 50–100+ later
each unit
69 numbers (health, map cell…) + embeddings of type, owner, order, items, buffs
map tokens
the 128×128 map (12 channels: trees, units, starts…) as 64 tiles
scalar token
1: gold, food, time, research, the last decisions
trunk
4 transformer blocks of width 256; a mask hides padding: any unit count works
memory
3 SSM layers carry the game; 1 attention layer looks back ≤ 64 steps
heads
10 in order, masked to legal choices: type → argument → aim → … → target → region → cell
critic
the position's value; also sees the opponent's numbers
precision
trunk bfloat16, heads float32; inference and learner agree to p99 0.04
3 · One game step

What a game waits through, four times a game-second

A game is idle while it waits for its decision, so this loop sets its speed.
A step takes ~58 ms from us-east sandboxes, ~72 ms from us-central: 4× game speed.
The learner is not in this loop.

  1. CPUThe game advances 250 ms and writes an observation.Sandbox, Wine~7 ms
  2. CPUThe game hook turns it into the model's tokens and legality masks.Sandbox, in the game (C)~0.1 ms
  3. NETThey cross to the game's actor.TCP tunnel½ of ~14–30 ms
  4. CPUThe actor sends them to inference.Actor~4 ms / 32 games
  5. GPUInference decides (section 4).Inference, GPU 1~17 ms
  6. CPUThe actor turns the decision into game commands and saves the step for the learner.Actor~2.5 ms / 32 games
  7. NETThe commands cross back; the game applies them.TCP tunnel½ of ~14–30 ms
4 · Inference

One recorded GPU program per batch size

A batch is whatever requests arrived in the last 2 ms.
Its step (model, heads, critic, each game's memory) is compiled and recorded once as a CUDA graph.
Each batch replays the recording with one launch: ~6 ms for ~46 games, ~2 ms of it on the GPU.
A recording fits one array size, but batches vary: in games, and in unit tokens (their fullest game's).
So batches are padded up to 64/128/256/512 games and 96/128/256 unit rows: 12 recordings,
all made at its first batch.

Where a request's ~17 ms goes (us-east actor)

  1. CPUWaits unread while the batch before it finishes.Inference process~6 ms
  2. CPUIts batch collects requests for up to 2 ms.Inference process~2 ms
  3. CPUJoin the requests; pack the inputs and masks into the recording's buffers.Inference process~1.5 ms
  4. GPUReplay the recorded step; copy the choices back.GPU 1~3.5 ms
  5. CPUAnswer each actor; the answer crosses to it.Inference process → actor~3.5 ms

The GPU's ~1.8 ms of it (58 games, 96 unit rows, offline)

encode
map, unit embeddings, tiles, 4 blocks: 1.1 ms
heads
10 in order, each masked: 0.26 ms
memory
3 SSM layers and the time attention: 0.16 ms
the rest
critic, each game's memory in and out: ~0.25 ms

Why two inference processes

A batch is ~2/3 CPU work (joining, packing, answering) and ~1/3 GPU.
One process cannot do both at once.
With two, each serving half the actors, one prepares while the other runs. Roughly to scale:

start
the 12 recordings: ~90 s with the Volume's compile cache, ~6 min without
weights
pulled every 1 s on a side thread, loaded between batches (~15 ms)
5 · The learner

From 128 chunks to new weights

Actors cut each learning player's game into 64-step chunks and send each as soon as it is done.
Every 128 chunks (8,192 steps) the learner on GPU 0 makes one PPO update.
Inference has the new weights within ~1 s.

Where an update's ~0.62 s of work goes (run sp28)

  1. GPUValue and reference passes: the critic and the frozen clone over all 8,192 steps.GPU 0~0.13 s
  2. GPU4 gradient steps of 2,048 steps each, the unit tokens packed (no padding).GPU 0~0.44 s
  3. CPUCopy the batch to the GPU; statistics; a save every 10 updates.Learner process~0.06 s
  4. CPUMeanwhile, on a side thread: build the next batch.Learner processoverlapped
then
it waits ~0.55 s for the next 128 chunks: the games make ~7,100 steps/s
losses
PPO clip 0.2 (dual 3), value, entropy 0.003, KL to the clone 0.2, auxiliary
advantages
GAE, γ 0.9999, λ 0.95
reward
+1 win, −1 loss, −1 at the 15-minute limit; nothing else
opponents
a ladder (the idle player, frozen clones, the built-in AI) plus self-play
lag
chunks more than 8 updates old are dropped
start
every unit-row size compiled before the first update

7 · GPUs and cost

Two H100s, mostly idle math

The model is narrow (width 256): thousands of small memory-bound steps around small matrix products.
GPU math used: ~1% of an H100 for inference, a few % for the learner.
GPU 1 is busy ~1/3 of the time (estimate).
GPU 1 exists so inference never waits behind the learner.

8 · Open

What would change this picture

  • Sandboxes in us-east only (made again until they land there; free): ~8,800 steps/s.
  • More games per container (e.g. 12 sandboxes) now that the learner and inference have room.
  • One H100 for learner and inference, or two A100s: one short run to compare.
  • A real bill for this layout.
  • A bigger model (the GPUs' math is mostly idle); positions for the time attention.
